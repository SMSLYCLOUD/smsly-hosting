# workflow
- Verify technical claims about third-party software syntax/behavior before making changes — especially when diagnosing production issues; consult documentation or the web rather than relying on assumptions. Confidence: 0.65
- Do not offer or attempt to SSH into the user's remote servers — debug and operate via their shell session or local access only. Confidence: 0.75
- Before committing changes to installer scripts (install.sh, lib/*.sh), thoroughly review exit code patterns and ensure failures warn but don't abort — do not commit until the error-handling flow is verified. Confidence: 0.80
- When stale or incorrect .env values are discovered (e.g., wrong hostnames, missing vars), add the fix to the installer scripts under lib/ rather than giving the user manual sed commands to run. Confidence: 0.85
- Review all unstaged changes before pushing — present a summary of each diff and wait for explicit approval before committing and pushing. Confidence: 0.70
- Before wiping/reinstalling a VPS or server, review and push all uncommitted code to remote — ensures no local-only changes are lost during a destructive operation. Confidence: 0.65
- For testing and mass-sending, prefer local/self-hosted test infrastructure over live providers — a local mail server on the user's PC (tunneled to the VPS) for email, local simulators/mock adapters for SMS/MMS/RCS — to avoid abusing VPS provider spam restrictions and provider limits. Confidence: 0.85
- When a review surfaces a list of gaps/issues and the user says "fix all" (or "yes" to a proposed fix list), fix everything in the list autonomously in one pass — do not stop to ask per item. Confidence: 0.80
- When asked to check how a feature is wired, sweep the entire ecosystem (all services, not just the obvious ones) and report per-service coverage, including gaps where the feature is expected but missing. Confidence: 0.70
- When explaining how a feature works, trace the full request flow: each service hop in order with file:line references, failure modes (fail-open vs fail-closed), and the total services touched. Confidence: 0.70
- When writing tests that use the DRF test client, use `TestCase` + manual `APIClient` instead of `APITestCase` to avoid pytest-django DB serialization issues with missing migration columns (e.g., `traffic_geo_enabled`). Confidence: 0.70
- Large, multi-system changes should enter plan mode and fan out parallel explore agents to map the gaps before writing any code, then get a written plan approved before implementing. Confidence: 0.70
- After shipping a large change, the user asks for a deep self-review ("review your works deeply") — audit every new call site against the real signatures in the codebase, fix what breaks, and report both the bugs caught and the assumptions explicitly cleared. Confidence: 0.75
- When a test fails after a change, confirm whether it is pre-existing by stashing the work and re-running on a pristine tree before claiming a regression (or clearing one) — and verify the stash pop restored the changes. Confidence: 0.75
- When an edit produces noisy whitespace/line-ending diff noise, use `git diff -w` to confirm the real content change set is only what was intended. Confidence: 0.70
- After edits, run the full verification ladder before reporting done: `py_compile` on every changed file, `manage.py check` for URL/wiring correctness, `npx tsc --noEmit` for the frontend, `bash -n` for shell, plus the targeted pytest suites — and report the result of each. Confidence: 0.75
- When a generated config/manifest is changed in one place, grep for every other generator or path that produces the same artifact and update them all — e.g. adding a middleware to a router means the docker-compose label generator, the local adapter, and the canary file builder all need the same change. Confidence: 0.70
- Keep migrations numbering consistent with the current leaf: check the latest migration number first and branch the new migration off it, rather than assuming a low number is still free. Confidence: 0.70
