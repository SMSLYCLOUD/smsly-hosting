# architecture
- Blue-green candidate containers that never became healthy should not be restarted — set restart policy to `no` for green candidates before promotion; only containers that were once healthy (i.e., promoted to live) should use `unless-stopped`. Confidence: 0.70
- The SMSLYCLOUD/ directory belongs to the parent company and is separate from the smsly-hosting (CloudNeuron) PaaS open-source project — do not treat it as part of the same product. Confidence: 0.65
- New installer functionality goes into separate files under lib/ and is sourced/linked from install.sh, not added directly to install.sh. Confidence: 0.75
- Kubernetes-related code (Helm charts, PodSecurity helpers, k8s templates) is no longer used — skip all k8s fixes and do not spend time on k8s-related work. Confidence: 0.70
- Do not modify SSH authentication settings (PasswordAuthentication, PermitRootLogin) in harden.sh — the platform manages SSH auth via scope key after provisioning. Confidence: 0.70
- Authentication uses DRF Token model (rest_framework.authtoken.models.Token), not djangorestframework-simplejwt. Do not import from rest_framework_simplejwt — it is not installed. Confidence: 0.75
- Container runtime bootstrap in harden.sh should try Kata first (requires KVM), fall back to gVisor, and persist the chosen runtime to CONTAINER_RUNTIME in .env so subsequent runs skip detection entirely. Confidence: 0.75
- Installer scripts should never block or abort the PaaS update — warn loudly about failures but always let the update proceed (do not use `return 1` or `exit 1` on recoverable failures). Even `exit 1` in sub-scripts called with `|| true` can affect the update flow — all exit codes in the install chain must be traced. Even `exit 0` in sub-scripts causes the parent installer to terminate early, preventing the rest of the update from running. Confidence: 0.88
- Work on SMSLYCLOUD itself (the services) — not the smsly-hosting (CloudNeuron) PaaS — when picking up tasks in this repo. Confidence: 0.90
- Customer-facing features must be white-labeled: the customer's own domain/branding fronts the feature (e.g., self-hosted verification pages that fetch Merkle proofs from the chain); platform URLs/branding are fallback defaults only and never forced into customer content. Confidence: 0.85
- Every email gets a chain hash id assigned automatically at accept time, regardless of whether any visible stamp/badge renders — the hash id is the trust anchor and the stamp is purely cosmetic. Confidence: 0.80
- Master node is the control plane and remote nodes (full/lite/media) are extensions of itself — every platform feature (runtime logs, monitoring/metrics/CPU load, console, storage analytics, mTLS/Envoy, scaling/HA/autoscaling, cloud storage, previews/safe-deploys) must work for remote deployments with full parity to master, with per-node visibility such as a dedicated Nodes section on the autoscaler page. Confidence: 0.85
- Deployed tenant services must keep serving when the Django control plane is offline/crashed — no single point of failure where Django outage breaks TLS/routing for all services. Confidence: 0.70
- For resilience-critical edge/host components that must survive Django/Docker outages, prefers single static binaries (Rust or Go) running as systemd services over containerized Python sidecars to minimize load and dependencies. Confidence: 0.75
- For those small single-binary helpers, prefers the language stdlib (Go `net/http`) over faster third-party servers (fasthttp/Fiber) — on loopback at low QPS the bottleneck is crypto, and a zero-dependency binary is easier to audit and own. Confidence: 0.65
- Internal platform infra services (secrets manager, apt/build caches, metrics, UI, app-security tooling) should be classified into sleep/throttle tiers and started on demand exactly like tenant workloads — minimize RAM/CPU to the lowest sustainable level rather than leaving every internal service permanently up. Confidence: 0.70
